# Now let's take the **same school-facility model** and look at it from a **production pipeline perspective**, where every pipeline run receives the latest source data and we use `MERGE`/upsert logic according to the required **SCD type**.

One important idea first:

> **`MERGE` is not itself an SCD strategy.**
> `MERGE` is the mechanism we use to compare source vs target. The SCD type determines **what we do when a match is found and something changed**.

Think:

```text
SOURCE
   ↓
Compare business key
   ↓
MATCHED / NOT MATCHED
   ↓
Detect changed columns
   ↓
SCD Type 0 / 1 / 2 / 3
   ↓
Apply appropriate action
```

I'll use **Snowflake-style `MERGE` syntax** below because it gives the cleanest production-style examples. The exact syntax differs in SQL Server, Oracle, Databricks, etc.

---

# 1. First Understand MATCHED vs NOT MATCHED

Suppose our target is:

```text
dim_facility
```

and today's source is:

```text
stg_facility
```

Target:

```text
facility_id | facility_name | status
-------------------------------------
SCH001      | School A      | ACTIVE
SCH002      | School B      | ACTIVE
SCH003      | School C      | ACTIVE
```

Today's source:

```text
facility_id | facility_name | status
-------------------------------------
SCH001      | School A      | ACTIVE
SCH002      | School B      | CLOSED
SCH004      | School D      | ACTIVE
```

Comparison:

```text
SCH001 → MATCHED + no change
SCH002 → MATCHED + changed
SCH003 → NOT MATCHED BY SOURCE
SCH004 → NOT MATCHED
```

These are **four different situations**.

---

# 2. The Basic MERGE Skeleton

```sql
MERGE INTO dim_facility AS tgt
USING stg_facility AS src

ON tgt.facility_id = src.facility_id

WHEN MATCHED THEN
    UPDATE SET
        tgt.facility_name = src.facility_name,
        tgt.operational_status = src.operational_status

WHEN NOT MATCHED THEN
    INSERT (
        facility_id,
        facility_name,
        operational_status
    )
    VALUES (
        src.facility_id,
        src.facility_name,
        src.operational_status
    );
```

Conceptually:

```text
                 SOURCE
                    |
                    ↓
             facility_id
                    |
              ┌─────┴─────┐
              │           │
           MATCHED     NOT MATCHED
              │           │
              ↓           ↓
           UPDATE       INSERT
```

But this is essentially **Type 1 behavior**.

---

# 3. Why You Should NOT Blindly Update Every MATCHED Row

This is a common beginner mistake:

```sql
WHEN MATCHED THEN
    UPDATE SET
        ...
```

Suppose:

```text
Source:
SCH001 | School A | ACTIVE

Target:
SCH001 | School A | ACTIVE
```

Nothing changed.

But the MERGE still performs an update.

That can cause:

* unnecessary writes
* unnecessary micro-partition changes
* unnecessary CDC events
* misleading audit information
* unnecessary downstream processing

So production pipelines usually do:

```sql
WHEN MATCHED
AND (
       tgt.facility_name <> src.facility_name
    OR tgt.operational_status <> src.operational_status
)
THEN UPDATE
```

Now:

```text
same → do nothing
changed → update
```

---

# 4. Handle NULL Correctly

This is extremely important.

Don't blindly write:

```sql
tgt.address <> src.address
```

because:

```text
NULL <> 'ABC'
```

doesn't evaluate to TRUE in normal SQL three-valued logic.

For Snowflake:

```sql
IS DISTINCT FROM
```

is safer.

Example:

```sql
WHEN MATCHED
AND (
       tgt.facility_name IS DISTINCT FROM src.facility_name
    OR tgt.address IS DISTINCT FROM src.address
    OR tgt.latitude IS DISTINCT FROM src.latitude
    OR tgt.longitude IS DISTINCT FROM src.longitude
)
THEN UPDATE
```

This correctly detects:

```text
NULL → value
value → NULL
value → different value
```

---

# 5. SCD Type 0 — Never Update

Let's say:

```text
establishment_date
```

is Type 0.

Source:

```text
SCH001 | 1985-06-15
```

Target:

```text
SCH001 | 1985-06-15
```

No problem.

But if source accidentally sends:

```text
SCH001 | 1987-06-15
```

we don't update it.

So:

```sql
MERGE INTO dim_facility_school tgt
USING stg_facility_school src
ON tgt.school_code = src.school_code

WHEN NOT MATCHED THEN
    INSERT (
        school_code,
        establishment_date,
        school_type,
        management_type
    )
    VALUES (
        src.school_code,
        src.establishment_date,
        src.school_type,
        src.management_type
    );
```

Notice:

**There is no `WHEN MATCHED THEN UPDATE`.**

That's intentional.

Existing record:

```text
MATCHED
    ↓
DO NOTHING
```

New school:

```text
NOT MATCHED
    ↓
INSERT
```

That's Type 0.

---

# 6. Type 0 Pipeline Thinking

```text
              SOURCE
                 |
                 ↓
          Is school_code
             existing?
           /           \
         YES            NO
          |              |
       NOTHING          INSERT
```

This is useful for attributes such as:

```text
original_establishment_date
original_source_id
original_registration_date
```

---

# 7. SCD Type 1 — Overwrite Current Value

Now consider:

```text
school_name
```

Suppose:

```text
Target
SCH001 | ZP High School

Source
SCH001 | Zilla Parishad High School
```

If business says historical name is irrelevant:

```text
old value → overwrite
```

MERGE:

```sql
MERGE INTO dim_facility tgt
USING stg_facility src

ON tgt.facility_id = src.facility_id

WHEN MATCHED
AND (
       tgt.facility_name IS DISTINCT FROM src.facility_name
    OR tgt.address IS DISTINCT FROM src.address
)
THEN UPDATE SET
    tgt.facility_name = src.facility_name,
    tgt.address = src.address,
    tgt.latitude = src.latitude,
    tgt.longitude = src.longitude,
    tgt.updated_at = CURRENT_TIMESTAMP

WHEN NOT MATCHED THEN
    INSERT (
        facility_id,
        facility_name,
        address,
        latitude,
        longitude,
        created_at,
        updated_at
    )
    VALUES (
        src.facility_id,
        src.facility_name,
        src.address,
        src.latitude,
        src.longitude,
        CURRENT_TIMESTAMP,
        CURRENT_TIMESTAMP
    );
```

---

# 8. Type 1 Result

Before:

```text
facility_key | facility_id | facility_name
-------------------------------------------
101           | SCH001      | ZP High School
```

After:

```text
facility_key | facility_id | facility_name
-------------------------------------------
101           | SCH001      | Zilla Parishad High School
```

No new row.

No history.

That's Type 1.

---

# 9. SCD Type 2 Is Different

Now suppose:

```text
management_type
```

must retain history.

Current:

```text
SCH001 | GOVERNMENT
```

Source:

```text
SCH001 | LOCAL_BODY
```

We **cannot simply update** the existing row.

We need:

```text
OLD ROW
↓
close it

NEW ROW
↓
insert new version
```

Result:

```text
facility_key | school | management | valid_from | valid_to   | current
-----------------------------------------------------------------------
1001         | SCH001 | GOVERNMENT  | 2020-01-01 | 2026-08-22 | N
1002         | SCH001 | LOCAL_BODY  | 2026-08-23 | NULL       | Y
```

---

# 10. The Type 2 Mental Model

Think:

```text
              SOURCE
                 |
                 ↓
         Business Key Exists?
           /            \
         NO              YES
         |                |
      INSERT          Did attributes
                       change?
                      /       \
                    NO         YES
                    |           |
                 NOTHING     CLOSE OLD
                                  +
                              INSERT NEW
```

That's the heart of SCD2.

---

# 11. Why a Single Simple MERGE Is Not Always Enough for SCD2

This is important.

A naive approach is:

```sql
WHEN MATCHED THEN UPDATE
WHEN NOT MATCHED THEN INSERT
```

But Type 2 needs:

```text
UPDATE existing row
+
INSERT new row
```

for **one source business key**.

A single straightforward MERGE isn't naturally suited to "update one target row and insert another new version for the same source row" in one matched branch.

Production implementations therefore commonly use:

```text
Stage
 ↓
Detect changes
 ↓
Expire current records
 ↓
Insert new versions
```

or a carefully designed two-step/expanded-source pattern depending on the platform.

For learning and maintainability, I strongly recommend the **two-step Type 2 pattern**.

---

# 12. Step 1 — Detect Changed Records

First identify what changed.

```sql
CREATE OR REPLACE TEMP TABLE changed_facilities AS
SELECT
    src.*
FROM stg_facility src
JOIN dim_facility tgt
    ON src.facility_id = tgt.facility_id
   AND tgt.is_current = TRUE

WHERE
       src.facility_name IS DISTINCT FROM tgt.facility_name
    OR src.address IS DISTINCT FROM tgt.address
    OR src.latitude IS DISTINCT FROM tgt.latitude
    OR src.longitude IS DISTINCT FROM tgt.longitude
    OR src.operational_status IS DISTINCT FROM tgt.operational_status;
```

Now:

```text
changed_facilities
```

contains only records requiring Type 2 action.

---

# 13. Step 2 — Close Existing Version

```sql
UPDATE dim_facility tgt
SET
    valid_to = CURRENT_DATE - 1,
    is_current = FALSE,
    updated_at = CURRENT_TIMESTAMP
WHERE tgt.is_current = TRUE
  AND EXISTS (
      SELECT 1
      FROM changed_facilities src
      WHERE src.facility_id = tgt.facility_id
  );
```

Suppose:

```text
Before:

1001 | SCH001 | GOVERNMENT | 2020-01-01 | NULL | TRUE
```

After:

```text
1001 | SCH001 | GOVERNMENT | 2020-01-01 | 2026-08-22 | FALSE
```

---

# 14. Step 3 — Insert New Version

```sql
INSERT INTO dim_facility
(
    facility_id,
    facility_type,
    facility_name,
    geography_key,
    address,
    latitude,
    longitude,
    operational_status,
    valid_from,
    valid_to,
    is_current,
    created_at
)
SELECT
    src.facility_id,
    src.facility_type,
    src.facility_name,
    src.geography_key,
    src.address,
    src.latitude,
    src.longitude,
    src.operational_status,
    CURRENT_DATE,
    NULL,
    TRUE,
    CURRENT_TIMESTAMP
FROM changed_facilities src;
```

Now:

```text
1001 | SCH001 | old values | 2020 | 2026-08-22 | FALSE
1002 | SCH001 | new values | 2026-08-23 | NULL | TRUE
```

---

# 15. But What About Completely New Schools?

Our `changed_facilities` only captured existing changed records.

We also need new schools.

We can do:

```sql
INSERT INTO dim_facility (...)
SELECT ...
FROM stg_facility src
LEFT JOIN dim_facility tgt
    ON src.facility_id = tgt.facility_id
WHERE tgt.facility_id IS NULL;
```

So the overall Type 2 pipeline becomes:

```text
                     STAGING
                        |
                        ↓
                Compare target
                        |
          ┌─────────────┼──────────────┐
          ↓             ↓              ↓
       NEW           SAME           CHANGED
        |              |               |
     INSERT         NOTHING        CLOSE OLD
                                         |
                                         ↓
                                    INSERT NEW
```

This is the clean mental model.

---

# 16. SCD Type 3

Suppose the business only wants:

```text
current_management_type
previous_management_type
```

Target:

```text
school_id
current_management
previous_management
```

Current:

```text
SCH001 | GOVERNMENT | NULL
```

Source:

```text
SCH001 | LOCAL_BODY
```

MERGE:

```sql
MERGE INTO dim_facility_school tgt
USING stg_facility_school src

ON tgt.school_code = src.school_code

WHEN MATCHED
AND tgt.management_type IS DISTINCT FROM src.management_type
THEN UPDATE SET
    tgt.previous_management_type = tgt.management_type,
    tgt.management_type = src.management_type

WHEN NOT MATCHED THEN
    INSERT (
        school_code,
        management_type,
        previous_management_type
    )
    VALUES (
        src.school_code,
        src.management_type,
        NULL
    );
```

Result:

```text
Before:

SCH001 | GOVERNMENT | NULL
```

After:

```text
SCH001 | LOCAL_BODY | GOVERNMENT
```

Another change:

```text
SCH001 | PRIVATE | LOCAL_BODY
```

The old `GOVERNMENT` is lost.

That's the limitation of Type 3.

---

# 17. Compare All Four SCD Types

This is worth memorizing conceptually.

| SCD    | Existing record changed | History         |
| ------ | ----------------------- | --------------- |
| Type 0 | Do nothing              | Original only   |
| Type 1 | Overwrite               | No history      |
| Type 2 | New version             | Full history    |
| Type 3 | Current + previous      | Limited history |

Example:

```text
Original:
GOVERNMENT
```

Then:

```text
LOCAL_BODY
```

Then:

```text
PRIVATE
```

### Type 0

```text
GOVERNMENT
```

### Type 1

```text
PRIVATE
```

### Type 2

```text
GOVERNMENT
LOCAL_BODY
PRIVATE
```

### Type 3

```text
current  = PRIVATE
previous = LOCAL_BODY
```

# 18. Now Apply This to Our School Model

I would classify attributes roughly like this:

### `dim_facility`

| Attribute          | SCD                                   |
| ------------------ | ------------------------------------- |
| facility_id        | Type 0                                |
| facility_name      | Type 1                                |
| address            | Type 2 if historical location matters |
| latitude           | Type 2 if historical location matters |
| longitude          | Type 2                                |
| operational_status | Type 2                                |
| facility_type      | Type 2/1 depending on business        |
| geography_key      | Type 2                                |

---

### `dim_facility_school`

| Attribute          | SCD                               |
| ------------------ | --------------------------------- |
| school_code        | Type 0                            |
| establishment_date | Type 0                            |
| school_name        | Type 1                            |
| management_type    | Type 2                            |
| school_type        | Type 2                            |
| gender_type        | Type 2                            |
| medium             | Type 2/1 depending on requirement |

---

### `fact_school_daily`

Don't use SCD.

If:

```text
2026-08-01 → classrooms = 10
2026-08-02 → classrooms = 10
2026-08-03 → classrooms = 12
```

these are **fact measurements**.

You simply insert the appropriate snapshot.

---

# 19. MERGE for Fact Snapshot

Suppose grain is:

```text
school + date
```

Then:

```sql
MERGE INTO fact_school_daily tgt
USING stg_school_daily src

ON  tgt.facility_key = src.facility_key
AND tgt.date_key = src.date_key

WHEN MATCHED
AND (
       tgt.total_students IS DISTINCT FROM src.total_students
    OR tgt.total_teachers IS DISTINCT FROM src.total_teachers
    OR tgt.classrooms_available IS DISTINCT FROM src.classrooms_available
    OR tgt.toilets_available IS DISTINCT FROM src.toilets_available
)
THEN UPDATE SET

    tgt.total_students = src.total_students,
    tgt.total_teachers = src.total_teachers,
    tgt.classrooms_available = src.classrooms_available,
    tgt.toilets_available = src.toilets_available,
    tgt.infrastructure_score = src.infrastructure_score

WHEN NOT MATCHED THEN
    INSERT (
        date_key,
        facility_key,
        total_students,
        total_teachers,
        classrooms_available,
        toilets_available,
        infrastructure_score
    )
    VALUES (
        src.date_key,
        src.facility_key,
        src.total_students,
        src.total_teachers,
        src.classrooms_available,
        src.toilets_available,
        src.infrastructure_score
    );
```

This is basically an **upsert**.

# 20. Now the Real Production Pipeline

Imagine today's source arrives.

```text
                    SOURCE
                       |
                       ↓
                  RAW LAYER
                       |
                       ↓
                 STAGING TABLE
                       |
                       ↓
              Data validation
                       |
                       ↓
             Deduplicate source
                       |
                       ↓
             Compare with target
                       |
          ┌────────────┼─────────────┐
          ↓            ↓             ↓
        NEW          SAME         CHANGED
          |            |             |
          ↓            ↓             ↓
       INSERT       NOTHING      SCD LOGIC
                                     |
                       ┌─────────────┼────────────┐
                       ↓             ↓            ↓
                     TYPE 1        TYPE 2       TYPE 3
                       ↓             ↓            ↓
                   UPDATE       CLOSE+INSERT   CURRENT+
                                                  PREVIOUS
```

That's how I would explain this in an interview.

# 21. One More Very Important Thing: Source Duplicates

Suppose today's staging table contains:

```text
SCH001 | School A | ACTIVE
SCH001 | School A | CLOSED
```

Now:

```sql
MERGE
```

may fail because one source key matches multiple rows.

So **before MERGE**, deduplicate.

For example:

```sql
CREATE OR REPLACE TEMP TABLE stg_facility_dedup AS
SELECT *
FROM (
    SELECT
        src.*,
        ROW_NUMBER() OVER (
            PARTITION BY facility_id
            ORDER BY updated_at DESC
        ) AS rn
    FROM stg_facility src
)
WHERE rn = 1;
```

Now:

```text
SCH001
```

has exactly one source record.

This is an extremely common production issue.

# 22. Another Important Edge Case: NULL

Suppose:

```text
Target:
latitude = 16.4441

Source:
latitude = NULL
```

Is that a change?

Probably yes.

Use:

```sql
IS DISTINCT FROM
```

rather than:

```sql
<>
```

for robust comparison.

---

# 23. Another Edge Case: Source Sends Old Data

Suppose target says:

```text
updated_at = 2026-08-23 10:00
```

but source sends:

```text
updated_at = 2026-08-20 10:00
```

You don't want the old record overwriting the newer one.

Add:

```sql
AND src.updated_at > tgt.updated_at
```

Example:

```sql
WHEN MATCHED
AND src.updated_at > tgt.updated_at
AND (
       tgt.address IS DISTINCT FROM src.address
    OR tgt.latitude IS DISTINCT FROM src.latitude
)
THEN UPDATE ...
```

This is **late/out-of-order data protection**.

---

# 24. Another Edge Case: Soft Delete

Suppose the source no longer sends:

```text
SCH005
```

Does that mean:

> School deleted?

Not necessarily.

It could mean:

* source extraction failed
* source filter changed
* temporary outage
* school closed
* school moved to another source
* record was accidentally deleted

So don't automatically do:

```text
NOT MATCHED BY SOURCE → DELETE
```

unless the source contract explicitly guarantees that missing rows mean deletion.

For facilities, I'd usually model:

```text
operational_status
```

such as:

```text
ACTIVE
CLOSED
MERGED
TEMPORARILY_CLOSED
```

---

# 25. If the Source Explicitly Sends Delete

Then we can handle it.

For example:

```text
src.operation = 'DELETE'
```

Then:

```sql
WHEN MATCHED
AND src.operation = 'DELETE'
THEN UPDATE SET
    tgt.operational_status = 'CLOSED',
    tgt.valid_to = CURRENT_DATE,
    tgt.is_current = FALSE;
```

Whether this is Type 1 or Type 2 depends on whether you retain the historical version.

---

# 26. The Golden Rule for Your Interview

When someone says:

> "How would you implement SCD using MERGE?"

Don't immediately start writing SQL.

First say:

> **"First I define the business key, then identify which attributes are Type 0, Type 1, Type 2 or Type 3, then compare the latest source record against the current target version. For unchanged records I do nothing; for new business keys I insert; for Type 1 changes I overwrite; and for Type 2 changes I expire the current version and create a new version."**

That's a **much stronger answer** than simply showing a MERGE statement.

---

# 27. The Complete Mental Model

Memorize this:

```text
                    BUSINESS KEY
                          |
                          ↓
                  Does target exist?
                    /           \
                  NO             YES
                  |               |
               INSERT       Is anything changed?
                              /          \
                            NO            YES
                            |              |
                         NOTHING      Which SCD?
                                          |
                     ┌────────────┬──────────────┬────────────┐
                     ↓            ↓              ↓            ↓
                   Type 0       Type 1         Type 2       Type 3
                     |            |              |            |
                  NOTHING       UPDATE       EXPIRE OLD   UPDATE CURRENT
                                               + INSERT    + PREVIOUS
```

And remember one more layer:

```text
              Is this attribute
                a dimension
                attribute?
                     |
             ┌───────┴────────┐
             |                |
            YES               NO
             |                |
           SCD            Is it a measurement?
                              |
                         ┌────┴─────┐
                         |          |
                        YES         NO
                         |          |
                      FACT      Re-evaluate model
```

That last decision prevents a **huge number of bad warehouse designs**.

For our school example:

```text
school_name                 → dimension → Type 1
management_type             → dimension → Type 2
establishment_date          → dimension → Type 0
previous_management_type    → dimension → Type 3
classrooms_today            → fact
students_today              → fact
distance_house_to_school    → fact
travel_time                 → fact
```
