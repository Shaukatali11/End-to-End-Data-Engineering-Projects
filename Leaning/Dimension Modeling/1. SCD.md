In **dimensional modeling**, Slowly Changing Dimension (SCD) is one of the most important concepts because it answers a fundamental question:

> **“What should happen when an attribute of a dimension changes?”**

For example, suppose your `Customer` dimension has:

| Customer_ID | Customer_Name | City      | State     |
| ----------- | ------------- | --------- | --------- |
| C101        | Ali           | Hyderabad | Telangana |

Tomorrow Ali moves to Bangalore.

Should we **overwrite Hyderabad**, or should we preserve the fact that he previously lived in Hyderabad?

That decision is exactly where **SCD** comes in.

---

# 1. First understand Dimension vs Fact

A typical warehouse might have:

### Dimension

`dim_customer`

| customer_key | customer_id | name  | city      | state     |
| -----------: | ----------- | ----- | --------- | --------- |
|          101 | C001        | Ali   | Hyderabad | Telangana |
|          102 | C002        | Rahim | Delhi     | Delhi     |

Dimension contains **descriptive information**.

### Fact

`fact_sales`

| date_key | customer_key | product_key | amount |
| -------: | -----------: | ----------: | -----: |
| 20260801 |          101 |         501 |   5000 |
| 20260802 |          101 |         502 |   3000 |

Fact contains **business events/measures**.

The important relationship is:

```text
                DIM_CUSTOMER
                     |
                     | customer_key
                     |
                     v
                FACT_SALES
```

Now imagine Ali changes city.

That is an **SCD problem**.

---

# 2. What exactly is Slowly Changing Dimension?

A Slowly Changing Dimension is a technique for managing changes in dimension attributes over time.

Examples:

* Customer changes address
* Employee changes department
* Product changes category
* Branch changes manager
* Supplier changes location
* Customer changes marital status
* Employee changes salary grade

The word **"slowly"** doesn't necessarily mean the change literally happens slowly.

It means dimension attributes generally change **less frequently than transactional facts**.

---

# 3. Why do we need SCD?

Suppose:

### January

Ali:

```text
Customer = C001
City = Hyderabad
```

He makes ₹10,000 purchases.

### February

Ali moves:

```text
Customer = C001
City = Bangalore
```

He makes ₹20,000 purchases.

Now management asks:

> "How much did Ali purchase while he was living in Hyderabad?"

If you simply overwrite:

```text
C001 | Ali | Bangalore
```

you have lost historical information.

That's why we need SCD strategies.

---

# 4. Main SCD Types

The most commonly discussed types are:

```text
SCD Type 0
SCD Type 1
SCD Type 2
SCD Type 3
SCD Type 4
SCD Type 6
```

There are also hybrid/custom implementations.

The most important for interviews and real-world data engineering are:

> **Type 1 and Type 2**

Type 2 is especially important.

---

# 5. SCD Type 0 — Never Change

Type 0 means:

> Once the dimension attribute is inserted, never update it.

Example:

```text
Customer_ID | Name | Original_City
C001        | Ali  | Hyderabad
```

Ali moves to Bangalore.

We **do nothing**.

Table remains:

```text
C001 | Ali | Hyderabad
```

### When useful?

For attributes that should represent the original value.

Examples:

* Original joining date
* Original customer registration branch
* Birth date
* Original customer category

Conceptually:

```text
Source
   |
   | change
   v
Dimension
   |
   X
Ignore change
```

---

# 6. SCD Type 1 — Overwrite

This is the simplest approach.

Initial:

| Customer_ID | Name | City      |
| ----------- | ---- | --------- |
| C001        | Ali  | Hyderabad |

Ali moves.

Update:

| Customer_ID | Name | City      |
| ----------- | ---- | --------- |
| C001        | Ali  | Bangalore |

The old value is lost.

### SQL

```sql
UPDATE dim_customer
SET city = 'Bangalore'
WHERE customer_id = 'C001';
```

### Advantage

Very simple.

### Disadvantage

Historical information is lost.

### When should we use Type 1?

When history isn't required.

Examples:

* Correcting spelling mistakes
* Correcting incorrect phone number
* Correcting bad source data
* Attributes where only the latest value matters

Example:

```text
Ali
```

was incorrectly loaded as:

```text
Ail
```

You don't need historical versions of a spelling mistake.

So Type 1 is perfect.

---

# 7. SCD Type 2 — Maintain Complete History

This is the most important SCD type.

Instead of updating the existing row, we:

1. Expire the old record
2. Insert a new record
3. Give the new record a new surrogate key
4. Maintain validity information

Example initial data:

| customer_key | customer_id | name | city      | current_flag | start_date | end_date |
| -----------: | ----------- | ---- | --------- | ------------ | ---------- | -------- |
|          101 | C001        | Ali  | Hyderabad | Y            | 2026-01-01 | NULL     |

Ali moves to Bangalore.

Instead of updating the row, we do:

### Old record

```text
101 | C001 | Ali | Hyderabad | N | 2026-01-01 | 2026-02-15
```

### New record

```text
205 | C001 | Ali | Bangalore | Y | 2026-02-16 | NULL
```

Final table:

| customer_key | customer_id | name | city      | current_flag | start_date | end_date   |
| -----------: | ----------- | ---- | --------- | ------------ | ---------- | ---------- |
|          101 | C001        | Ali  | Hyderabad | N            | 2026-01-01 | 2026-02-15 |
|          205 | C001        | Ali  | Bangalore | Y            | 2026-02-16 | NULL       |

Now history is preserved.

---

# 8. Why do we need Surrogate Key in Type 2?

This is extremely important.

You have:

```text
customer_id = C001
```

This is the **business/natural key**.

It identifies the real customer.

But Type 2 requires multiple versions:

```text
C001 → Hyderabad
C001 → Bangalore
C001 → Chennai
```

Therefore we need another key:

```text
customer_key
```

Example:

| customer_key | customer_id | city      |
| -----------: | ----------- | --------- |
|          101 | C001        | Hyderabad |
|          205 | C001        | Bangalore |
|          309 | C001        | Chennai   |

So:

```text
customer_id
    ↓
Business identity

customer_key
    ↓
Version identity
```

This is one of the most important concepts in dimensional modeling.

---

# 9. Type 2 with Fact Tables

Suppose Ali purchases something in Hyderabad.

```text
fact_sales

customer_key = 101
amount = 5000
```

Later Ali moves to Bangalore.

New customer dimension:

```text
101 | C001 | Hyderabad
205 | C001 | Bangalore
```

New sales transaction:

```text
customer_key = 205
amount = 8000
```

Therefore:

```text
Old transaction
      ↓
customer_key = 101
      ↓
Hyderabad version


New transaction
      ↓
customer_key = 205
      ↓
Bangalore version
```

This lets us answer:

> "How much did customers from Hyderabad purchase?"

without losing historical context.

---

# 10. Type 3 — Limited History

Type 3 stores the current value and previous value.

Example:

| Customer_ID | Name | Current_City | Previous_City |
| ----------- | ---- | ------------ | ------------- |
| C001        | Ali  | Bangalore    | Hyderabad     |

Ali moves to Chennai:

| Customer_ID | Name | Current_City | Previous_City |
| ----------- | ---- | ------------ | ------------- |
| C001        | Ali  | Chennai      | Bangalore     |

Hyderabad is lost.

So Type 3 gives us **limited history**, generally one previous value.

### Type 2 vs Type 3

Type 2:

```text
Hyderabad
Bangalore
Chennai
```

All versions preserved.

Type 3:

```text
Current = Chennai
Previous = Bangalore
```

Only limited history.

---

# 11. SCD Type 4 — Separate History Table

In Type 4, we maintain:

```text
Current Dimension
+
Historical Dimension
```

Example:

### Current

`dim_customer`

| customer_id | name | city      |
| ----------- | ---- | --------- |
| C001        | Ali  | Bangalore |

### History

`dim_customer_history`

| customer_id | name | city      | start_date | end_date   |
| ----------- | ---- | --------- | ---------- | ---------- |
| C001        | Ali  | Hyderabad | 2026-01-01 | 2026-02-15 |

The current table contains only current data.

The history table contains historical versions.

---

# 12. SCD Type 6 — Hybrid

Type 6 combines:

```text
Type 1
+
Type 2
+
Type 3
```

That's why:

```text
6 = 1 + 2 + 3
```

It can maintain:

* complete history
* current value
* previous/current attributes

This is more complex and is used when the business has specific historical reporting requirements.

---

# 13. Quick Comparison

| Type   | History                     | Method                 |
| ------ | --------------------------- | ---------------------- |
| Type 0 | No change                   | Keep original          |
| Type 1 | No                          | Overwrite              |
| Type 2 | Complete                    | New row                |
| Type 3 | Limited                     | Previous column        |
| Type 4 | Complete                    | Separate history table |
| Type 6 | Complete + current/previous | Hybrid                 |

For most practical projects:

```text
Type 1 → corrections/current-state attributes

Type 2 → historical business changes
```

## 14.1 Business Key / Natural Key

Example:

```text

```

This identifies the customer from the source system.

You need this to determine:

> "Is this the same customer or a new customer?"

# 15. Surrogate Key

Warehouse dimension should generally have a surrogate key.

Example:

```text
customer_key
```

Usually generated by:

* Identity column
* Sequence
* Auto increment
* Delta/Spark logic
* Warehouse-generated key

Example:

```text
customer_id | customer_key
C001        | 101
C002        | 102
```

Not every dimension column necessarily needs SCD treatment.

Suppose:

```text

```

Business may say:


So you need a **column-level SCD strategy**.

This is very important.

Type 2 needs to know:

> When did this version become valid?

Example:

```text

```

Example:

```text

```

# 18. Expiration Date

You also need:

```text
effective_end_date
```

Example:

```text
2026-02-15
```


```text
NULL
```

For example:

| Customer | City      | Start  | End        |

# 19. Current Flag

Common implementation:

```text
is_current
```

Example:

```text
Y
N
```

or:

```text
1
0
```

Example:

| customer_id | city      | is_current |
| ----------- | --------- | ---------- |
| C001        | Hyderabad | 0          |
| C001        | Bangalore | 1          |

This makes finding the latest version easy.

```sql

```

# 20. Hashing — Very Important in Modern Data Engineering

Suppose your dimension has:

```text
name
city
state
country
phone
email
```

How do you efficiently determine whether anything changed?

You can compare every column.

But that's cumbersome.

Instead, create a hash.

For example:

```text
hash(
    name,
    city,
    state,
    country,
    phone
)
```

Example:

```text
C001 | Ali | Hyderabad | Telangana | HASH123
```

After source change:

```text
C001 | Ali | Bangalore | Karnataka | HASH987
```

Since:

```text
HASH123 != HASH987
```

we know the dimension changed.

This is extremely common in modern ETL/ELT pipelines.

# 21. Source vs Target

Suppose today's source contains:

### Source

| customer_id | name  | city      |
| ----------- | ----- | --------- |
| C001        | Ali   | Bangalore |
| C002        | Rahim | Delhi     |
| C003        | Ahmed | Mumbai    |

Target dimension:

| customer_key | customer_id | name  | city      |
| -----------: | ----------- | ----- | --------- |
|          101 | C001        | Ali   | Hyderabad |
|          102 | C002        | Rahim | Delhi     |

We compare using:

```text
Business Key
```

Then determine:

```text
New?
Changed?
Unchanged?
Deleted?
```

This is the core SCD logic.

# 22. SCD Type 2 Processing Logic

Think of it as:

```text
                 SOURCE
                    |
                    ↓
             Read today's data
                    |
                    ↓
          Match business key
                    |
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      New       Unchanged     Changed
        |           |           |
        ↓           ↓           ↓
   Insert row     Ignore    Expire old
                              +
                           Insert new
```

This is the heart of SCD Type 2.

# 25. SQL Implementation Concept

Suppose:

### Target

```text
dim_customer
```

### Source

```text
stg_customer
```

We first identify changed records.

Conceptually:

```sql
SELECT s.*
FROM stg_customer s
JOIN dim_customer d
  ON s.customer_id = d.customer_id
WHERE d.is_current = 1
AND s.hash_value <> d.hash_value;
```

These are the records requiring Type 2 processing.

Then:

### Step 1

Expire old record:

```sql
UPDATE dim_customer
SET
    is_current = 0,
    end_date = CURRENT_DATE
WHERE customer_id = 'C001'
AND is_current = 1;
```

### Step 2

Insert new version:

```sql
INSERT INTO dim_customer
(
    customer_key,
    customer_id,
    name,
    city,
    start_date,
    end_date,
    is_current
)
VALUES
(
    103,
    'C001',
    'Ali',
    'Bangalore',
    CURRENT_DATE,
    '9999-12-31',
    1
);
```

Since you're working with **Databricks and data engineering**, this is particularly important.

```text

   ↓
Bronze
   ↓
Silver
   ↓
```

```text

       ↓
     Bronze
       ↓
     Silver
       ↓
 dim_customer
```

In Databricks, Delta tables allow you to perform operations such as:

```text

```

and maintain transactional consistency.

---

# 27. SCD Type 2 Using MERGE

A conceptual Delta approach looks like:

```sql
MERGE INTO dim_customer d
USING staging_customer s
ON d.customer_id = s.customer_id
AND d.is_current = true

WHEN MATCHED
AND d.hash_value <> s.hash_value
THEN UPDATE SET
    d.is_current = false,
    d.end_date = current_date()

WHEN NOT MATCHED
THEN INSERT (...);
```

But there's an important issue:

**A simple MERGE isn't always sufficient for Type 2.**

Why?

Because a changed record needs:

```text
1. UPDATE old version
2. INSERT new version
```

So production implementations often use a more carefully designed staging/merge strategy, or Delta Lake's supported SCD patterns.

# 29. What Happens When a Record Is Deleted?

This is another thing you need to decide **before implementing SCD**.

Suppose:

```text
C001 | Ali | Bangalore
```

exists in the dimension.

Tomorrow source doesn't contain C001.

Does that mean:

```text
Customer deleted?
```

Not necessarily.

It could mean:

* source extraction failed
* customer inactive
* source system removed record
* data filtering changed

Therefore deletion strategy must be explicitly defined.

Possible approaches:

### Soft delete

```text
is_deleted = true
```

### Expire Type 2 record

```text
is_current = false
end_date = today
```

### Ignore deletion

Depending on business requirements.

# 31. One Very Important Concept: Source Key vs Surrogate Key

Suppose:

```text
Source:

customer_id = C001
```

Dimension:

```text
customer_key = 101
customer_id = C001
```

After change:

```text
customer_key = 205
customer_id = C001
```

So:

```text
customer_id = same
customer_key = different
```

This allows:

```text
C001
 ├── 101 → Hyderabad
 └── 205 → Bangalore
```

This is the essence of Type 2.

# 32. What Happens to Existing Fact Records?

This is a very important real-world question.

Suppose:

```text
Fact:

date = Jan 10
customer_key = 101
amount = 5000
```

Later customer changes.

New dimension:

```text
101 → Hyderabad
205 → Bangalore
```

We **do not update the old fact** from:

```text
101
```

to:

```text
205
```

The old fact should remain associated with the historical dimension version.

That's what makes historical reporting work.

# 34. How Do You Convert an Existing Dimension into SCD Type 2?

This is a very important real-world scenario.

Suppose you already have:

```text
dim_customer
```

and currently it's Type 1.

Current table:

| customer_key | customer_id | name  | city      |
| -----------: | ----------- | ----- | --------- |
|          101 | C001        | Ali   | Bangalore |
|          102 | C002        | Rahim | Delhi     |

You now want Type 2.

### First question:

> Do you have historical source data?

If **YES**, you can potentially reconstruct historical versions.

If **NO**, you cannot magically recover historical changes that were overwritten.

This is critical.

---

# 35. Existing Type 1 → Type 2

Suppose current dimension is:

```text
C001 | Ali | Bangalore
```

You don't know whether Ali previously lived in:

```text
Hyderabad
Delhi
Mumbai
```

That information is already lost.

Therefore you can create:

```text
C001 | Ali | Bangalore | current
```

with:

```text
start_date = migration_date
end_date = 9999-12-31
is_current = 1
```

But you **cannot reconstruct previous history** unless you have:

* source historical tables
* CDC data
* audit tables
* database logs
* old snapshots
* backups
* previous warehouse tables
* archived files

# 36. Migration Strategy

Suppose current Type 1 dimension:

```text
dim_customer
```

You want:

```text
dim_customer_scd2
```

### Step 1 — Add SCD columns

Add:

```text
effective_start_date
effective_end_date
is_current
record_hash
```

Example:

| customer_id | city      | start      | end        | current |
| ----------- | --------- | ---------- | ---------- | ------- |
| C001        | Bangalore | 2026-08-14 | 9999-12-31 | 1       |

This becomes the initial baseline.

---

# 37. Step 2 — Create Hash

For example:

```text
hash(name, city, state, country)
```

Store it:

```text
C001 | Ali | Bangalore | Karnataka | ABC123
```

---

# 38. Step 3 — Start Incremental Processing

Tomorrow source:

```text
C001 | Ali | Chennai | Tamil Nadu
```

Hash becomes:

```text
XYZ789
```

Compare:

```text
ABC123 != XYZ789
```

Therefore:

```text
CHANGE DETECTED
```

---

# 39. Step 4 — Expire Existing Version

```text
C001 | Ali | Bangalore | 2026-08-14 | 2026-08-15 | 0
```

---

# 40. Step 5 — Insert New Version

```text
C001 | Ali | Chennai | 2026-08-15 | 9999-12-31 | 1
```

Now:

| key | customer | city      | start  | end    | current |
| --: | -------- | --------- | ------ | ------ | ------- |
| 101 | C001     | Bangalore | Aug 14 | Aug 15 | 0       |
| 205 | C001     | Chennai   | Aug 15 | 9999   | 1       |

Now your dimension behaves as Type 2.

# 42. Two More Advanced Topics

Once you understand basic SCD, learn these next.

### Late-arriving dimensions

Fact arrives before its dimension.

```text
Fact arrives
     ↓
Customer doesn't exist yet
     ↓
What customer_key should fact use?
```

Usually handled using an **unknown/inferred member**.

Example:

```text
customer_key = -1
```

Later the actual dimension arrives.

---

### Late-arriving dimension changes

Suppose you receive a historical customer update today, but its effective date was three months ago.

You can't simply use today's date.

You may need to split the historical timeline.

Example:

```text
Jan ───── Mar ───── Jun
       Change
```

This is much more advanced Type 2 processing.

# 43. The Complete Mental Model

Think about SCD like a **version history of an entity**.

```text
                    CUSTOMER C001
                         |
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       Version 1      Version 2      Version 3
       Hyderabad      Bangalore       Chennai
       Jan-Mar        Mar-Jun         Jun-now
          |              |              |
       key=101         key=205        key=309
```

The business key stays:

```text
C001
```

The surrogate key changes:

```text
101 → 205 → 309
```

That is the central idea behind SCD Type 2.
