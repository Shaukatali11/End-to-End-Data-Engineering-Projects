# Let's design it as if a **State Education Department** wants an analytical warehouse for school facilities.

The goal is not just to create tables. We want to answer questions such as:

* How many schools exist in each district/mandal/village?
* Which schools serve the largest population?
* What is the average distance from households to their nearest school?
* Which schools have poor infrastructure?
* How many schools were established before 2000?
* How many students/households are served by each school?
* How did school infrastructure change over time?
* Which households are more than 5 km from a school?
* Which mandals have poor school coverage?
* What happens if a school moves?
* What happens if a school changes management/category?
* Can we report historical infrastructure correctly?

---

# 1. First — Think About the Business Before Tables

Let's assume the state has:

```text
1 State
   ↓
10 Districts
   ↓
Mandal
   ↓
Village
   ↓
Household
   ↓
School
```

For our small example, we'll use:

```text
State: Andhra Pradesh
Districts: Krishna, Guntur, Prakasam
Mandals: a few sample mandals
Villages: several villages
Schools: 10
Households: 20
```

The real production system could have:

```text
thousands of schools
millions of households
millions of school-household relationships
```

That scale is important because it influences our fact-table design.

# 3. Very Important: Don't Put Household in `dim_geography`

You suggested:

> `dim_geo_info id, state, district, mandal, village and household id`

I would **not** put `household_id` directly into `dim_geography`.

Why?

Because these have different grains.

### Geography

One row could represent:

> One village.

### Household

One row represents:

> One household.

If we put household into geography:

```text
state
district
mandal
village
household_id
```

then the geography dimension becomes effectively **household grain**.

You lose the clean meaning of the geography dimension.

Instead:

```text
dim_geography
```

and:

```text
dim_household
```

should be separate.

Relationship:

```text
dim_geography
      ↑
      |
dim_household
```

This is an important modeling decision.

```text
                         dim_geography
```

More precisely:

```text

```

# 5. Why `dim_facility` + `dim_facility_school`?

This is another important modeling decision.

A school is a **type of facility**.

Tomorrow the department may also manage:

```text
schools
hospitals
clinics
libraries
community centers
hostels
training centers
```

So we can create:

```text
dim_facility
```

for common attributes:

```text
facility_key
facility_id
facility_type
facility_name
geography_key
address
latitude
longitude
```

Then:

```text
dim_facility_school
```

for school-specific information:

```text
facility_key
school_code
school_type
management_type
establishment_date
classes_from
classes_to
```

Conceptually:

```text
                    FACILITY
                       |
            ┌──────────┴──────────┐
            |                     |
         SCHOOL                HOSPITAL
            |                     |
    school-specific         hospital-specific
       attributes              attributes
```

This is basically a **supertype/subtype model**.

# 9. Warehouse `dim_geography`

Now we create our actual dimensional model.

### Grain

> **One row represents one geography entity at a defined geographic level.**

We can support:

```text
STATE
DISTRICT
MANDAL
VILLAGE
```

using a hierarchy.

```sql
CREATE TABLE dim_geography (
    geography_key       INT AUTO_INCREMENT PRIMARY KEY,

    geography_id        VARCHAR(30) NOT NULL,
    geography_level     VARCHAR(20) NOT NULL,

    state_code          VARCHAR(10),
    state_name          VARCHAR(100),

    district_code       VARCHAR(20),
    district_name       VARCHAR(100),

    mandal_code         VARCHAR(20),
    mandal_name         VARCHAR(100),

    village_code        VARCHAR(20),
    village_name        VARCHAR(100),

    parent_geography_key INT NULL,

    created_at           DATETIME DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_geography
        UNIQUE (geography_id, geography_level)
);
```

---

# 10. Why `geography_key`?

Never depend exclusively on:

```text
district_name
```

or:

```text
village_name
```

because names can change or be duplicated.

For example:

```text
village = Ramapuram
```

could exist in multiple mandals.

So we want:

```text
geography_key
```

as our warehouse surrogate key.

---

# 11. Geography Example

We might have:

```text
geography_key | geography_id | level    | state | district | mandal | village
--------------------------------------------------------------------------------
1             | AP           | STATE    | AP    | NULL     | NULL   | NULL
2             | D001         | DISTRICT | AP    | Krishna  | NULL   | NULL
3             | M001         | MANDAL   | AP    | Krishna  | Gudivada
4             | V001         | VILLAGE  | AP    | Krishna  | Gudivada | Mallavolu
```

The important concept is:

> **The geography dimension has its own grain and hierarchy.**

# 12. `dim_household`

Now household is a separate dimension.

### Grain

> One row represents one household.

```sql
CREATE TABLE dim_household (
    household_key       BIGINT AUTO_INCREMENT PRIMARY KEY,

    household_id        VARCHAR(30) NOT NULL,

    geography_key       INT NOT NULL,

    latitude            DECIMAL(10,7),
    longitude           DECIMAL(10,7),

    population_count    INT,

    household_type      VARCHAR(50),

    created_at          DATETIME DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_household
        UNIQUE (household_id),

    FOREIGN KEY (geography_key)
        REFERENCES dim_geography(geography_key)
);
```

# 13. Now `dim_facility`

This is the common facility master.

### Grain

> One row represents one physical facility.

```sql
CREATE TABLE dim_facility (
    facility_key        BIGINT AUTO_INCREMENT PRIMARY KEY,

    facility_id         VARCHAR(30) NOT NULL,

    facility_type       VARCHAR(50) NOT NULL,

    facility_name       VARCHAR(200),

    geography_key       INT,

    address             VARCHAR(300),

    latitude            DECIMAL(10,7),
    longitude           DECIMAL(10,7),

    operational_status  VARCHAR(30),

    valid_from          DATE,
    valid_to            DATE,

    is_current          BOOLEAN DEFAULT TRUE,

    created_at          DATETIME DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_facility
        UNIQUE (facility_id, valid_from),

    FOREIGN KEY (geography_key)
        REFERENCES dim_geography(geography_key)
);
```

---

# 14. Why do we have `valid_from`, `valid_to`, `is_current`?

This is because we may use **SCD Type 2** on facility attributes.

Suppose:

```text
School A
Village X
```

moves to:

```text
Village Y
```

We don't necessarily overwrite the old record.

Instead:

```text
facility_key | facility_id | village | valid_from | valid_to | current
-----------------------------------------------------------------------
101          | SCH001      | X       | 2010-01-01 | 2025-06-30 | N
102          | SCH001      | Y       | 2025-07-01 | NULL       | Y
```

Now historical reporting remains possible.

# 17. Fact Table

```sql
CREATE TABLE fact_school_household (
    school_household_key BIGINT AUTO_INCREMENT PRIMARY KEY,

    date_key             INT NOT NULL,

    facility_key         BIGINT NOT NULL,

    household_key        BIGINT NOT NULL,

    distance_km          DECIMAL(10,3),

    population_served    INT,

    school_capacity      INT,

    capacity_utilization DECIMAL(10,4),

    travel_time_minutes  INT,

    is_nearest_school    BOOLEAN,

    within_1km            BOOLEAN,
    within_3km            BOOLEAN,
    within_5km            BOOLEAN,

    created_at           DATETIME DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_school_household_date
        UNIQUE (
            date_key,
            facility_key,
            household_key
        ),

    FOREIGN KEY (facility_key)
        REFERENCES dim_facility(facility_key),

    FOREIGN KEY (household_key)
        REFERENCES dim_household(household_key)
);
```

---

# 18. But Wait — Is `population_served` really a measure?

This is where you should think critically.

Suppose:

```text
Household H001
Population = 5
```

and:

```text
School S001
```

If the household is assigned to that school, we could have:

```text
population_served = 5
```

But if the same household appears against three schools:

```text
H001 → S001 → 5
H001 → S002 → 5
H001 → S003 → 5
```

then:

```sql
SUM(population_served)
```

gives:

```text
15
```

while the actual household population is only:

```text
5
```

This is a classic **fact-grain / aggregation problem**.

---

# 19. How Would a Professional Fix This?

We need to know what the relationship means.

### Option A — Every household has exactly one assigned school

Then the fact can contain:

```text
household_key
school_key
population_served
```

and the relationship is one-to-one from household assignment perspective.

### Option B — Every household can be related to multiple nearby schools

Then:

```text
distance
```

is valid for every relationship.

But:

```text
population_served
```

should **not automatically be additive** across all schools.

We could instead have:

```text
distance_km
is_nearest_school
```

and calculate population served only from:

```text
is_nearest_school = TRUE
```

### Better model

Potentially:

```text
fact_school_household_distance
```

for distance:

> one household × one school × one date

and another fact:

```text
fact_school_population
```

for:

> one school × one date

This is a very important modeling distinction.

---

# 20. I Would Actually Separate These Two Facts

For a production model, I'd seriously consider:

```text
fact_school_household_distance
```

and:

```text
fact_school_daily
```

# 21. `fact_school_household_distance`

```sql
CREATE TABLE fact_school_household_distance (
    date_key            INT NOT NULL,

    facility_key        BIGINT NOT NULL,
    household_key       BIGINT NOT NULL,

    distance_km         DECIMAL(10,3),

    travel_time_minutes INT,

    is_nearest_school   BOOLEAN,

    within_1km          BOOLEAN,
    within_3km          BOOLEAN,
    within_5km          BOOLEAN,

    PRIMARY KEY (
        date_key,
        facility_key,
        household_key
    ),

    FOREIGN KEY (facility_key)
        REFERENCES dim_facility(facility_key),

    FOREIGN KEY (household_key)
        REFERENCES dim_household(household_key)
);
```

### Grain

> One household-school-distance relationship on one date.

---

# 22. `fact_school_daily`

This captures school-level measurements.

```sql
CREATE TABLE fact_school_daily (
    date_key               INT NOT NULL,

    facility_key           BIGINT NOT NULL,

    total_students         INT,
    total_teachers         INT,

    population_served      INT,

    classrooms_available   INT,
    classrooms_required    INT,

    toilets_available      INT,
    drinking_water         BOOLEAN,
    electricity_available  BOOLEAN,

    infrastructure_score   DECIMAL(5,2),

    PRIMARY KEY (
        date_key,
        facility_key
    ),

    FOREIGN KEY (facility_key)
        REFERENCES dim_facility(facility_key)
);
```

### Grain

> One school for one day.

Now the model is much cleaner.

---

# 23. Why Two Facts Are Better Here

Because they represent different business processes.

### Distance fact

```text
School × Household × Date
```

### School snapshot

```text
School × Date
```

They have different grains.

This avoids putting:

```text
school-level metrics
```

into:

```text
household-school-level fact
```

and accidentally duplicating them.

This is exactly the type of reasoning interviewers want.

```text

        ↓

```

with strings everywhere.

We want to resolve:

```text
school_id

     ↓
```

For example, conceptually:

```text
SCH001
  ↓
Mallavolu
  ↓
V001
  ↓

  ↓
```

# 32. SCD Type 0 in This Model

Some attributes should **never change** from the warehouse perspective.

For example:

```text
establishment_date
```

A school established on:

```text
1985-06-15
```

should not suddenly become:

```text
1990-06-15
```

unless the source was wrong.

So we can treat:

```text
establishment_date
```

as **SCD Type 0**.

### Type 0

> Preserve the original value.

If source sends:

```text
1985-06-15
```

then we don't overwrite it during normal updates.

### Good candidates

* original establishment date
* original facility ID
* original registration date
* original source identifier

---

# 33. SCD Type 1

Consider:

```text
school_name
```

Suppose:

```text
"ZP High School Mallavolu"
```

has a spelling correction:

```text
"Zilla Parishad High School Mallavolu"
```

If historical school names don't matter, Type 1 is reasonable.

Simply:

```sql
UPDATE dim_facility
SET facility_name = 'Zilla Parishad High School Mallavolu'
WHERE facility_id = 'SCH001'
  AND is_current = TRUE;
```

History is overwritten.

# 34. SCD Type 2

Suppose school management changes:

```text
GOVERNMENT
```

to:

```text
LOCAL_BODY
```

and historical reporting matters.

Then:

### Old row

```text
facility_key = 1001
school = SCH001
management = GOVERNMENT
valid_from = 1985
valid_to = 2026-06-30
current = N
```

### New row

```text
facility_key = 1101
school = SCH001
management = LOCAL_BODY
valid_from = 2026-07-01
valid_to = NULL
current = Y
```

This lets you answer:

> "How many schools were government-managed in 2025?"

without rewriting history.

---

# 35. SCD Type 3

Suppose the education department only wants:

```text
current_management_type
previous_management_type
```

Then:

```text
school_id
current_management
previous_management
```

Example:

```text
SCH001 | LOCAL_BODY | GOVERNMENT
```

This gives limited history.

### When useful?

When the business only asks:

> "What is the current value and what was it previously?"

It avoids the complexity of Type 2.

# 36. What About Infrastructure?

Now think carefully.

Suppose:

```text
SCH001
classrooms = 10
```

Then two years later:

```text
classrooms = 14
```

Should this go into SCD Type 2?

I would question that.

Infrastructure is often better modeled as a **periodic snapshot**.

```text
fact_school_daily
```

or perhaps:

```text
fact_school_yearly
```

Example:

```text
date       school   classrooms
2024       SCH001   10
2025       SCH001   12
2026       SCH001   14
```

Why?

Because:

> "How many classrooms did the school have in 2025?"

is a **measurement/state question**, not necessarily a dimension-history question.

This distinction is extremely important.

# 39. One Important Edge Case: "Nearest School"

Suppose:

```text
HH001
```

has:

```text
SCH001 → 2.1 km
SCH002 → 1.7 km
SCH003 → 5.8 km
```

Then:

```text
SCH002 = nearest
```

We can store:

```text
is_nearest_school = TRUE
```

for SCH002.

But don't assume:

> nearest = assigned school.

A household may be assigned to School A even though School B is geographically closer.

So we may eventually need:

```text
assigned_school_key
```

separate from:

```text
nearest_school_key
```

This is a **very important real-world distinction**.

---

# 40. Another Edge Case: Road Distance vs Straight-Line Distance

Our latitude/longitude can calculate straight-line distance.

But actual travel may be:

```text
Straight-line = 2 km
Road distance = 4.7 km
```

So don't name the column:

```text
distance_km
```

without defining it.

Better:

```text
straight_line_distance_km
road_distance_km
travel_time_minutes
```

Then the business knows exactly what the metric means.

---

# 41. Another Edge Case: School Capacity

Suppose:

```text
SCH001
capacity = 400
students = 520
```

We can derive:

```text
capacity_utilization = 520 / 400
                     = 1.30
                     = 130%
```

This tells us the school is over capacity.

But don't store every derived metric unnecessarily.

Depending on the warehouse design, we could calculate:

```sql
total_students / NULLIF(school_capacity, 0)
```

at query time or materialize it if heavily used.

---

# 42. Another Edge Case: School Closed

Suppose:

```text
SCH005
```

closes on:

```text
2026-06-30
```

Should it disappear?

No.

Historical facts should still point to it.

We might have:

```text
operational_status = CLOSED
```

and:

```text
closure_date = 2026-06-30
```

The facility remains queryable historically.

---

# 43. Another Edge Case: School Relocation

This is where SCD Type 2 becomes extremely useful.

Suppose:

```text
SCH008
```

moves from:

```text
Village A
```

to:

```text
Village B
```

We should not overwrite the location if historical analysis matters.

Instead:

```text
facility_key | school_id | geography | lat | lon | from | to
----------------------------------------------------------------
5001         | SCH008    | Village A | ... | ... | 1972 | 2026
5002         | SCH008    | Village B | ... | ... | 2026 | NULL
```

Then historical distance facts can continue referencing the correct facility version.

---

# 44. One More Important Modeling Decision

There is a subtle question:

> Should `facility_key` in the distance fact point to the current facility or the historical SCD2 version?

If geography/location is SCD Type 2, then for historical distance calculations:

**Use the version valid at the measurement date.**

For example:

```text
2025 distance
    ↓
facility_key = 5001

2026 distance
    ↓
facility_key = 5002
```

This gives correct historical geography.

# 45. The Most Important Grain Statements in This Model

I would document these explicitly.

### `dim_geography`

> One row represents one geographic entity at a defined hierarchy level.

### `dim_household`

> One row represents one household.

### `dim_facility`

> One row represents one version of a physical facility.

### `dim_facility_school`

> One row represents one version of school-specific attributes for a facility.

### `fact_school_daily`

> One row represents one school for one measurement date.

### `fact_school_household_distance`

> One row represents one household-to-school relationship for one measurement date.

These statements are more important than the SQL itself.

# 47. And Here Is the Professional Reasoning Behind It

The most important thing is **not**:

> "I know star schema."

The important reasoning is:

```text
Business requirement
        ↓
Identify business process
        ↓
Define grain
        ↓
Separate entities with different grain
        ↓
Identify facts
        ↓
Identify dimensions
        ↓
Determine historical requirements
        ↓
Choose SCD strategy
        ↓
Define metric semantics
        ↓
Prevent many-to-many multiplication
        ↓
Handle late-arriving data
        ↓
Handle relocation / closure / changes
        ↓
Optimize for analytical consumption
```

For this school system specifically, I'd make these **five decisions very explicit in an interview**:

### Decision 1

**Don't put household directly into geography.**

Because geography and household have different grains.

### Decision 2

**Separate school-level snapshots from household-school relationships.**

Because:

```text
school/day
```

and:

```text
school/household/day
```

are different grains.

### Decision 3

**Use SCD Type 2 for attributes where historical context matters.**

Especially:

* facility location
* management
* operational status
* important classification

### Decision 4

**Use Type 1 for corrections/current-only attributes.**

For example, a spelling correction to the school name.

### Decision 5

**Use Type 0 for immutable attributes.**

For example:

```text
original establishment date
source registration ID
```
